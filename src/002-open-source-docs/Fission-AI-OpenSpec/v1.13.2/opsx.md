# OPSX 工作流

> 欢迎在 [Discord](https://discord.gg/YctCnvvshC) 提供反馈。

## 它是什么？

OPSX 现在是 OpenSpec 的标准工作流。

它是一个 **流畅的、迭代的工作流**，用于 OpenSpec 变更。不再有严格的阶段 — 只有你可以随时采取的行动。

## 为什么存在

旧的 OpenSpec 工作流有效，但它是 **锁定阶段** 的：

- **指令是硬编码的** — 埋在 TypeScript 中，你无法更改它们
- **全有或全无** — 一个大命令创建所有内容，无法测试单个部分
- **固定结构** — 每个人的工作流都一样，无法自定义
- **黑盒** — 当 AI 输出不好时，你无法调整提示

**OPSX 打开了它。** 现在任何人都可以：

1. **试验指令** — 编辑模板，看看 AI 是否做得更好
2. **细粒度测试** — 独立验证每个产物的指令
3. **自定义工作流** — 定义你自己的产物和依赖关系
4. **快速迭代** — 更改模板，立即测试，无需重新构建

```
旧工作流:                      OPSX:
┌────────────────────────┐           ┌────────────────────────┐
│  硬编码在包中            │           │  schema.yaml           │◄── 你编辑这个
│  (无法更改)              │           │  templates/*.md        │◄── 或这个
│        ↓               │           │        ↓               │
│  等待新版本              │           │  立即生效               │
│        ↓               │           │        ↓               │
│  希望它更好              │           │  你自己测试             │
└────────────────────────┘           └────────────────────────┘
```

**这对每个人都适用：**
- **团队** — 创建与你实际工作方式匹配的工作流
- **高级用户** — 调整提示以获得更好的 AI 输出
- **OpenSpec 贡献者** — 无需发布即可试验新方法

我们都在学习什么最有效。OPSX 让我们可以一起学习。

## 用户体验

**线性工作流的问题：**
你"在规划阶段"，然后"在实施阶段"，然后"完成"。但真实工作不会那样运作。你实施某些东西，意识到你的设计是错的，需要更新 specs，继续实施。线性阶段与工作的实际方式作斗争。

**OPSX 方法：**
- **行动，而非阶段** — 创建、实现、更新、归档 — 随时都可以做
- **依赖关系是使能器** — 它们展示什么可做，而不是下一步必须做什么

```
  proposal ──→ specs ──→ design ──→ tasks ──→ implement
```

## 设置

```bash
# 确保你已安装 openspec — 技能会自动生成
openspec init
```

这会创建 `.claude/skills/`（或等效目录）中的技能，AI 编码助手会自动检测。

默认情况下，OpenSpec 使用 `core` 工作流配置文件（`propose`、`explore`、`apply`、`update`、`sync`、`archive`）。如果你想要扩展工作流命令（`new`、`continue`、`ff`、`verify`、`bulk-archive`、`onboard`），用 `openspec config profile` 配置它们，然后应用 `openspec update`。

设置期间，你会被提示创建 **项目配置**（`openspec/config.yaml`）。这是可选但推荐的。

## 项目配置

项目配置让你可以设置默认值，并将项目特定的上下文注入到所有产物中。

### 创建配置

配置在 `openspec init` 期间创建，或手动创建：

```yaml
# openspec/config.yaml
schema: spec-driven

context: |
  技术栈: TypeScript, React, Node.js
  API 约定: RESTful, JSON 响应
  测试: Vitest 用于单元测试，Playwright 用于 e2e
  风格: ESLint with Prettier, strict TypeScript

rules:
  proposal:
    - 包含回滚计划
    - 确定受影响的团队
  specs:
    - 使用 Given/When/Then 格式编写场景
  design:
    - 为复杂流程包含序列图
```

### 配置字段

| 字段 | 类型 | 描述 |
|-------|------|-------------|
| `schema` | string | 新变更的默认模式（例如 `spec-driven`） |
| `context` | string | 注入到所有产物指令中的项目上下文 |
| `rules` | object | 按产物 ID 键入的每个产物规则 |

### 工作原理

**模式优先级**（从高到低）：
1. CLI 标志 (`--schema <name>`)
2. 变更元数据（变更目录中的 `.openspec.yaml`）
3. 项目配置（`openspec/config.yaml`）
4. 默认值（`spec-driven`）

**上下文注入：**
- 上下文被添加到每个产物的指令之前
- 包裹在 `<context>...</context>` 标签中
- 帮助 AI 理解你项目的约定

**规则注入：**
- 规则只注入到匹配的产物中
- 包裹在 `<rules>...</rules>` 标签中
- 出现在上下文之后、模板之前

### 产物 ID by 模式

**spec-driven**（默认）：
- `proposal` — 变更提案
- `specs` — 规格说明
- `design` — 技术设计
- `tasks` — 实现任务

### 配置验证

- `rules` 中的未知产物 ID 会生成警告
- 模式名称会针对可用模式进行验证
- 上下文有 50KB 大小限制
- 无效的 YAML 会报告行号

### 故障排除

**"Unknown artifact ID in rules: X"**
- 检查产物 ID 是否与你的模式匹配（参见上面的列表）
- 运行 `openspec schemas --json` 查看每个模式的产物 ID

**配置未应用：**
- 确保文件位于 `openspec/config.yaml`（不是 `.yml`）
- 用验证器检查 YAML 语法
- 配置更改立即生效（无需重启）

**上下文太大：**
- 上下文限制为 50KB
- 改为总结或链接到外部文档

## 命令

| 命令 | 作用 |
|---------|--------------|
| `/opsx:propose` | 创建变更并一步生成规划产物（默认快速路径） |
| `/opsx:explore` | 思考想法、调查问题、澄清需求 |
| `/opsx:new` | 开始新的变更脚手架（扩展工作流） |
| `/opsx:continue` | 创建下一个产物（扩展工作流） |
| `/opsx:ff` | 快速推进规划产物（扩展工作流） |
| `/opsx:apply` | 实现任务，按需更新产物 |
| `/opsx:update` | 修订变更的规划产物并保持它们的一致性 |
| `/opsx:verify` | 验证实现是否符合产物（扩展工作流） |
| `/opsx:sync` | 将 delta specs 合并到主 specs（可选） |
| `/opsx:archive` | 完成后归档 |
| `/opsx:bulk-archive` | 同时归档多个变更（扩展工作流） |
| `/opsx:onboard` | 引导式端到端变更演示（扩展工作流） |

## 用法

### 探索想法
```
/opsx:explore
```
思考想法、调查问题、比较选项。不需要结构 — 只是一个思考伙伴。当洞察结晶时，过渡到 `/opsx:propose`（默认）或 `/opsx:new`/`/opsx:ff`（扩展）。

### 开始新变更
```
/opsx:propose
```
创建变更并生成实施前所需的规划产物。

如果你已启用扩展工作流，你可以使用：

```text
/opsx:new        # 仅脚手架
/opsx:continue   # 一次创建一个产物
/opsx:ff         # 一次创建所有规划产物
```

### 创建产物
```
/opsx:continue
```
根据依赖关系显示准备好创建的内容，然后创建一个产物。反复使用以逐步构建你的变更。

```
/opsx:ff add-dark-mode
```
一次创建所有规划产物。当你清楚知道要构建什么时使用。

### 实现（流畅的部分）
```
/opsx:apply
```
执行任务，勾选它们。如果你正在处理多个变更，你可以运行 `/opsx:apply <name>`；否则它应该从对话中推断，并在无法判断时提示你选择。

### 更新变更
```
/opsx:update add-dark-mode - 我们现在把主题存在 cookie 里
```
修订变更的现有规划产物并保持它们在任何方向上的一致性（设计编辑可能会波及到 proposal）。它从不编辑代码。每次编辑都会先与你确认。参见 [update 参考](commands.md#opsxupdate) 了解它如何处理缺失文件而不创建新产物。

如果你的修订改变了变更的 *意图*，请重新开始。参见 [何时更新 vs 重新开始](#when-to-update-vs-start-fresh)。

### 同步 delta specs
```text
/opsx:sync
```
将当前变更的 delta specs 合并到你的主 `openspec/specs/` 中，而不归档 — 变更保持活跃。它应用整个 delta：`## REMOVED` 下的需求从主 spec 中删除，重命名的需求就地重命名，而 delta 未提及的内容保持不变。同步是可选的 — 归档会在需要时提示你先同步。当你想在归档前更新主 specs、当并行变更需要构建在此变更刚添加的 specs 上时，或当你想在归档前审查合并后的主 spec 时，使用它。

### 完成
```
/opsx:archive   # 完成后移动到归档（如有需要提示同步 specs）
```

## 何时更新 vs 重新开始

你可以在实施之前随时编辑你的 proposal 或 specs。但什么时候精炼变成了"这是不同的工作"？

### Proposal 捕捉什么

Proposal 定义三件事：
1. **意图** — 你在解决什么问题？
2. **范围** — 什么在范围内/外？
3. **方法** — 你将如何解决它？

问题是：什么变了，变了多少？

### 更新现有变更时：

**相同意图，精炼执行**
- 你发现没考虑到的边缘情况
- 方法需要调整但目标未变
- 实现揭示设计略有偏差

**范围缩小**
- 你意识到完整范围太大，想先交付 MVP
- "添加 dark mode" → "添加 dark mode 切换（系统偏好设置 v2）"

**学习驱动的修正**
- 代码库结构不是你想象的那样
- 依赖项不像预期的那样工作
- "使用 CSS 变量" → "改用 Tailwind 的 dark: prefix"

### 开始新变更时：

**意图根本改变**
- 问题本身现在不同了
- "添加 dark mode" → "添加带有自定义颜色、字体、间距的综合主题系统"

**范围爆炸**
- 变更增长太多，本质上是不同的工作
- 原始 proposal 更新后无法辨认
- "修复登录 bug" → "重写认证系统"

**原始可完成**
- 原始变更可以标记为"完成"
- 新工作独立存在，不是精炼
- 完成 "添加 dark mode MVP" → 归档 → 新变更 "增强 dark mode"

### 启发式方法

```
                        ┌─────────────────────────────────────┐
                        │     这是同一项工作吗？                 │
                        └──────────────┬──────────────────────┘
                                       │
                    ┌──────────────────┼──────────────────┐
                    │                  │                  │
                    ▼                  ▼                  ▼
             Same intent?      >50% overlap?      Can original
             Same problem?     Same scope?        be "done" without
                    │                  │          these changes?
                    │                  │                  │
          ┌────────┴────────┐  ┌──────┴──────┐   ┌───────┴───────┐
          │                 │  │             │   │               │
         YES               NO YES           NO  NO              YES
          │                 │  │             │   │               │
          ▼                 ▼  ▼             ▼   ▼               ▼
       UPDATE            NEW  UPDATE       NEW  UPDATE          NEW
```

| 测试 | 更新 | 新变更 |
|------|--------|------------|
| **身份** | "同一件事，精炼" | "不同的工作" |
| **范围重叠** | >50% 重叠 | <50% 重叠 |
| **完成度** | 不完成这些更改就无法"完成" | 可以完成原始的，新工作是独立的 |
| **故事** | 更新链讲述连贯的故事 | 补丁会比澄清更混乱 |

### 原则

> **更新保留上下文。新变更提供清晰度。**
>
> 当你的思考历史有价值时选择更新。
> 当重新开始比修补更清晰时选择新变更。

把它想象成 git 分支：
- 在同一功能上工作时保持提交
- 当它是真正的新工作时开始新分支
- 有时合并部分功能并为第 2 阶段重新开始

## 有什么不同？

| | 旧版 (`/openspec:proposal`) | OPSX (`/opsx:*`) |
|---|---|---|
| **结构** | 一个大的 proposal 文档 | 具有依赖关系的离散产物 |
| **工作流** | 线性阶段：规划 → 实施 → 归档 | 流畅行动 — 随时做任何事 |
| **迭代** | 尴尬地回去 | 学习时更新产物 |
| **自定义** | 固定结构 | 模式驱动（定义你自己的产物） |

**关键洞察：** 工作不是线性的。OPSX 不再假装它是。

## 架构深入

本节解释 OPSX 在底层如何工作以及它与旧工作流的比较。
本节中的示例使用扩展命令集（`new`、`continue` 等）；默认 `core` 用户可以将相同流程映射为 `propose → apply → sync → archive`。

### 哲学：阶段 vs 行动

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         旧工作流                                               │
│                    (阶段锁定，全有或全无)                                       │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ┌──────────────┐      ┌──────────────┐      ┌──────────────┐             │
│   │   规划阶段     │ ───► │   实施阶段     │ ───► │   归档阶段     │             │
│   └──────────────┘      └──────────────┘      └──────────────┘             │
│         │                     │                     │                       │
│         ▼                     ▼                     ▼                       │
│   /openspec:proposal   /openspec:apply      /openspec:archive              │
│                                                                             │
│   • 一次创建所有产物                                                          │
│   • 无法在实施期间返回更新 specs                                             │
│   • 阶段门控强制执行线性进度                                                  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘


┌─────────────────────────────────────────────────────────────────────────────┐
│                            OPSX 工作流                                        │
│                      (流畅行动，迭代式)                                        │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│              ┌────────────────────────────────────────────┐                 │
│              │           行动（不是阶段）                   │                 │
│              │                                            │                 │
│              │   new ◄──► continue ◄──► apply ◄──► archive │                 │
│              │    │          │           │           │    │                 │
│              │    └──────────┴───────────┴─────────────┘    │                 │
│              │              any order                        │                 │
│              └────────────────────────────────────────────┘                 │
│                                                                             │
│   • 一次创建一个产物或快速推进                                               │
│   • 在实施期间更新 specs/design/tasks                                       │
│   • 依赖关系启用进度，阶段不存在                                               │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 组件架构

**旧工作流** 使用 TypeScript 中的硬编码模板：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                      旧工作流组件                                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   硬编码模板 (TypeScript 字符串)                                              │
│                    │                                                        │
│                    ▼                                                        │
│   特定工具的配置器/适配器                                                     │
│                    │                                                        │
│                    ▼                                                        │
│   生成的命令文件 (.claude/commands/openspec/*.md)                             │
│                                                                             │
│   • 固定结构，无产物感知                                                       │
│   • 更改需要修改代码 + 重新构建                                                │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**OPSX** 使用外部模式和依赖关系图引擎：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         OPSX 组件                                            │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   模式定义 (YAML)                                                            │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │  name: spec-driven                                                  │   │
│   │  artifacts:                                                         │   │
│   │    - id: proposal                                                   │   │
│   │      generates: proposal.md                                         │   │
│   │      requires: []              ◄── 依赖关系                         │   │
│   │    - id: specs                                                      │   │
│   │      generates: specs/**/*.md  ◄── Glob 模式                        │   │
│   │      requires: [proposal]      ◄── 在 proposal 之后启用            │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                    │                                                        │
│                    ▼                                                        │
│   产物图引擎                                                                   │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │  • 拓扑排序（依赖关系排序）                                           │   │
│   │  • 状态检测（文件系统存在性）                                         │   │
│   │  • 丰富指令生成（模板 + 上下文）                                       │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                    │                                                        │
│                    ▼                                                        │
│   技能文件 (.claude/skills/openspec-*/SKILL.md)                               │
│                                                                             │
│   • 跨编辑器兼容（Claude Code、Cursor、Devin）                               │
│   • 技能查询 CLI 以获取结构化数据                                           │
│   • 通过模式文件完全可自定义                                                │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 依赖关系图模型

产物形成有向无环图（DAG）。依赖关系是 **使能器**，不是门：

```
                              proposal
                             (根节点)
                                  │
                    ┌─────────────┴─────────────┐
                    │                           │
                    ▼                           ▼
                 specs                       design
              (requires:                  (requires:
               proposal)                   proposal)
                    │                           │
                    └─────────────┬─────────────
                                  │
                                  ▼
                               tasks
                           (requires:
                           specs, design)
                                  │
                                  ▼
                          ┌──────────────┐
                          │ APPLY 阶段   │
                          │ (requires:   │
                          │  tasks)      │
                          └──────────────┘
```

**状态转换：**

```
   BLOCKED ────────────────► READY ────────────────► DONE
      │                        │                       │
   Missing                  All deps               File exists
   dependencies             are DONE               on filesystem
```

### 信息流

**旧工作流** — 代理接收静态指令：

```
  User: "/openspec:proposal"
           │
           ▼
  ┌─────────────────────────────────────────┐
  │  静态指令：                               │
  │  • 创建 proposal.md                       │
  │  • 创建 tasks.md                        │
  │  • 创建 design.md                       │
  │  • 创建 delta spec 文件                   │
  │                                         │
  │  不知道存在什么或                         │
  │  产物之间的依赖关系                       │
  └─────────────────────────────────────────┘
           │
           ▼
  Agent creates ALL artifacts in one go
```

**OPSX** — 代理查询丰富上下文：

```
  User: "/opsx:continue"
           │
           ▼
  ┌──────────────────────────────────────────────────────────────────────────┐
  │  步骤 1：查询当前状态                                                     │
  │  ┌────────────────────────────────────────────────────────────────────┐  │
  │  │  $ openspec status --change "add-auth" --json                      │  │
  │  │                                                                    │  │
  │  │  {                                                                 │  │
  │  │    "artifacts": [                                                  │  │
  │  │      {"id": "proposal", "status": "done"},                         │  │
  │  │      {"id": "specs", "status": "ready"},      ◄── 第一个就绪       │  │
  │  │      {"id": "design", "status": "ready"},                          │  │
  │  │      {"id": "tasks", "status": "blocked",                          │  │
  │  │       "missingDeps": ["specs", "design"]}                          │  │
  │  │    ]                                                               │  │
  │  │  }                                                                 │  │
  │  └────────────────────────────────────────────────────────────────────┘  │
  │                                                                          │
```

### 迭代模型

**旧工作流** — 尴尬地迭代：

```
  ┌─────────┐     ┌─────────┐     ┌─────────┐
  │/proposal│ ──► │ /apply  │ ──► │/archive │
  └─────────┘     └─────────┘     └─────────┘
       │               │
       │               ├── "等等，设计是错的"
       │               │
       │               ├── 选项：
       │               │   • 手动编辑文件（破坏上下文）
       │               │   • 放弃并重新开始
       │               │   • 推进并稍后修复
       │               │
       │               └── 没有官方的"回去"机制
       │
       └── 一次创建所有产物
```

**OPSX** — 自然迭代：

```
  /opsx:new ───► /opsx:continue ───► /opsx:apply ───► /opsx:archive
      │                │                  │
      │                │                  ├── "设计是错的"
      │                │                  │
      │                │                  ▼
      │                │            直接编辑 design.md
      │                │            然后继续！
      │                │                  │
      │                │                  ▼
      │                │         /opsx:apply 从你停下的地方继续
      │                │
      │                └── 创建一个产物，显示解锁的内容
      │
      └── 搭建变更，等待指示
```

### 自定义模式

使用模式管理命令创建自定义工作流：

```bash
# 从头创建新模式（交互式）
openspec schema init my-workflow

# 或复刻现有模式作为起点
openspec schema fork spec-driven my-workflow

# 验证你的模式结构
openspec schema validate my-workflow

# 查看模式从哪解析（用于调试）
openspec schema which my-workflow
```

模式存储在 `openspec/schemas/`（项目本地，版本控制）或 `~/.local/share/openspec/schemas/`（用户全局）。

**模式结构：**
```
openspec/schemas/research-first/
├── schema.yaml
└── templates/
    ├── research.md
    ├── proposal.md
    └── tasks.md
```

**示例 schema.yaml：**
```yaml
name: research-first
artifacts:
  - id: research        # 在 proposal 之前添加
    generates: research.md
    requires: []

  - id: proposal
    generates: proposal.md
    requires: [research]  # 现在依赖于 research

  - id: tasks
    generates: tasks.md
    requires: [proposal]
```

**依赖关系图：**
```
   research ──► proposal ──► tasks
```

### 总结

| 方面 | 旧版 | OPSX |
|--------|----------|------|
| **模板** | 硬编码 TypeScript | 外部 YAML + Markdown |
| **依赖关系** | 无（一次全部） | DAG 与拓扑排序 |
| **状态** | 基于阶段的心智模型 | 文件系统存在性 |
| **自定义** | 编辑源文件，重新构建 | 创建 schema.yaml |
| **迭代** | 阶段锁定 | 流畅，随时编辑 |
| **编辑器支持** | 特定工具配置器/适配器 | 单一技能目录 |

## 模式

模式定义存在哪些产物及其依赖关系。目前可用：

- **spec-driven**（默认）：proposal → specs → design → tasks

```bash
# 列出可用模式
openspec schemas

# 查看所有模式及其解析来源
openspec schema which --all

# 交互式创建新模式
openspec schema init my-workflow

# 复刻现有模式进行自定义
openspec schema fork spec-driven my-workflow

# 使用前验证模式结构
openspec schema validate my-workflow
```

## 技巧

- 在承诺变更之前使用 `/opsx:explore` 思考想法
- 当你知道想要什么时用 `/opsx:ff`，在探索时用 `/opsx:continue`
- 在 `/opsx:apply` 期间，如果有东西错了 — 修正产物，然后继续
- 通过 `tasks.md` 中的复选框跟踪进度
- 随时检查状态：`openspec status --change "name"`
