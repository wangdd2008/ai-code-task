# 探索优先

**`/opsx:explore` 是你的思考伙伴。每当你有问题但还没有计划时，就拿起它。** 它会调查你的代码库，与你权衡选项，并澄清你真正想要什么，所有这一切都在写任何代码之前。当画面清晰时，它会移交给 `/opsx:propose`。

如果你从这些文档中只带走一个习惯，就带走这个：**当你不确定时，先探索再提出。**

这就是重要的原因。AI 编码助手很热心。模糊地询问，它们会自信地构建 *某样东西*，只是可能不是你需要的。探索就是解药。这是一个无风险的对话，你和 AI 一起想出正确的行动，所以当你提出时，你在提出正确的东西。

## 何时探索

探索作为第一步的频率比人们预期的要高。当以下任何一项为真时使用它：

- 你知道 *问题* 但不知道 *解决方案*。（"页面感觉很慢。""认证一团糟。""我们不断收到重复订单。"）
- 你在选择方法之间，想要针对你的实际代码列出权衡。
- 你新接触一个代码库，需要在更改之前了解某些东西是如何工作的。
- 需求模糊，你想在承诺之前把它们弄清楚。
- 你怀疑工作比你看起来更大或更小，想要诚实地确定范围。

只有当你已经确切知道想要什么和怎么做时才跳过探索。在这种情况下直接去 [`/opsx:propose`](commands.md#opsxpropose)。

## 它做什么（和不做什么）

探索是一个 **对话**，不是生成器。

**它会：**
- 阅读和搜索你的代码库以回答真正的问题。
- 比较选项并命名每种方法的权衡。
- 绘制图表使设计清晰易读。
- 帮助你缩小一个模糊的想法，使之成为具体的、可构建的范围。
- 在你要求时捕捉探索结果，或在你接受其提议时：它会用 `openspec new change` 搭建变更并写入你命名的规划产物，或更新现有变更的产物。
- 在你准备好时过渡到 `/opsx:propose`。

**它不会：**
- 编写或修改代码。探索永远不会在任何路径上写代码，包括捕捉。
- 设计或编辑你的模式或模板。塑造那些是变更，不是思考。
- 自动开始变更或写入产物。它不会写任何东西，除非你要求，或在你同意它提供时，而且只写你同意的那些东西，加上变更需要的设置文件（见下文）。
- 催促你捕捉。当思路结晶时它提供；你决定。

这就是重点。探索不花你任何东西，也不会承诺任何东西，直到你说可以。你可以探索三个死胡同，从中学到东西，然后才提出幸存下来的路径。

## 它已安装

好消息：`/opsx:explore` 随默认的 **core** 配置文件一起提供，就在 `propose`、`apply`、`update`、`sync` 和 `archive` 旁边。你不需要启用任何东西。如果 OpenSpec 已在你的项目中设置好，探索就在你的 AI 聊天中准备好了。（和所有 `/opsx:*` 命令一样，你在助手聊天中输入它，而不是在终端中。参见 [命令如何工作](how-commands-work.md)。）

## 一个完整示例

看看一个模糊的担忧如何变成一个锋利的、可构建的变更。

```text
You: /opsx:explore

AI:  你想探索什么？

You: 我们的 checkout 有时会创建重复订单。我不知道为什么，
     也不知道如何安全地修复它。

AI:  让我深入 checkout 路径...
     [读取订单服务、支付 webhook 处理程序和
     客户端提交逻辑]

     这是我找到的。有两种方式可以产生重复：

     1. 客户端可以提交两次（双击、慢网络重试）。
        没有任何东西去抖动它。
     2. 支付 webhook 可以触发多次，而处理程序
        每次都创建订单。没有幂等键。

     原因 #2 是危险的：它可能收费并履行两次。

     三种修复方法，大致按健壮性排序：
     - 在订单创建端点上使用幂等键（同时处理两个原因）
     - 通过支付意图 id 在 webhook 上去重（只处理 #2）
     - 客户端去抖动（只处理 #1，掩盖了真正的 bug）

     鉴于你的代码已经存储了支付意图 id，
     幂等键方法是一个小改动，回报最大。
     要确定范围吗？

You: 是的，我们做幂等键。

You: /opsx:propose add-order-idempotency-key

AI:  已创建 openspec/changes/add-order-idempotency-key/，proposal
     和 delta spec 基于我们刚才的发现。准备实现。
```

注意发生了什么。起点是"有些问题，我不敢碰"。二十秒的探索把它变成了命名根本原因、三种排序选项、与现有代码相关的建议，以及一个精确的变更。接下来的 proposal 之所以清晰，是因为思考先发生了。

## 移交给 propose

探索不会归档任何东西。当你准备好时，你只需开始一个变更，AI 会将对话中的上下文带入产物。

```text
explore  ──►  propose  ──►  apply  ──►  archive
 (思考)     (同意)       (构建)      (记录)
```

你可以用自然语言说（"把这个变成变更"）或直接运行 `/opsx:propose <name>`。无论哪种方式，你刚做的探索都成为 proposal 的基础，不是一次性的聊天。

你还可以要求探索捕捉变更本身，而不离开对话："start a change for this" 搭建文件夹，"write the proposal too" 写入你命名的产物。搭建还会放置变更的元数据，并填充你的项目顶层可能缺失的任何内容（`openspec/specs/`、`openspec/changes/archive/`、`config.yaml`）。

这是与移交相同的目的地，只有一个区别：propose 写入你的模式要求到达实现所需的全部产物集，而捕捉只写入你命名的产物。

如果你使用扩展命令集，探索可以移交给 `/opsx:new` 代替，用于逐步创建产物。参见 [工作流](workflows.md)。

## 良好探索的技巧

- **带来问题，不是解决方案。** "登录感觉很慢" 给 AI 调查的空间。"添加 Redis 缓存" 让你承诺了一个未经测试的答案。
- **大声要求权衡。** "每种方法的缺点是什么？" 会让你得到更诚实的比较。
- **让它先读取。** 最好的探索从 AI 实际查看你的代码开始，而不是猜测。如果有助于它，指向相关区域。
- **退出是可以的。** 如果探索揭示了这个想法不值得做，那就是胜利。你以低成本学到了东西。
- **变更中途再次探索。** 在 `/opsx:apply` 期间卡住了？你可以退回探索一个子问题，然后回来。

## 诚实的权衡

**你得到什么：** 探索在最便宜的时刻捕捉错误转向 — 在你承诺任何东西之前。它在不熟悉的代码中尤其强大，AI 读取和总结系统的能力节省了你一个下午的探索时间。

**它花费什么：** 一点耐心。探索是对话，所以它比直接运行 `/opsx:propose` 并祈祷要慢。对于你真正理解的工作，这个额外步骤纯粹是开销，你应该跳过它。

经验法则：任务越模糊，探索的回报越大。任务越清晰，你越容易直接跳到提出。
