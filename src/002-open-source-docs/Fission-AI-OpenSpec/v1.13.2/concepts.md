# 概念

本指南解释了 OpenSpec 背后的核心思想以及它们如何组合在一起。有关实际用法，请参阅[开始使用](getting-started.md)和[工作流](workflows.md)。

## 哲学

OpenSpec 围绕四个原则构建：

```
流动而非僵化    — 没有阶段关卡，做任何有意义的工作
迭代而非瀑布    — 边做边学，边走边优化
简单而非复杂    — 轻量级设置，最小仪式
棕地优先        — 适用于现有代码库，不仅仅是绿地
```

### 为什么这些原则很重要

**流动而非僵化。**传统的规格系统将你锁定在阶段中：首先规划，然后实现，然后完成。OpenSpec 更灵活 — 你可以按对任何有意义的工作顺序创建产物。

**迭代而非瀑布。**需求会变化。理解会深化。开始看起来不错的方法在看到代码库后可能站不住脚。OpenSpec 接受这一现实。

**简单而非复杂。**某些规格框架需要大量设置、严格的格式或繁重的流程。OpenSpec 不挡路。几秒钟初始化，立即开始工作，仅在需要时自定义。

**棕地优先。**大多数软件工作不是从零开始构建 — 而是修改现有系统。OpenSpec 的差异方法使指定现有行为更改变得容易，不仅仅是描述新系统。

## 大图景

OpenSpec 将你的组织工作分为两个主要区域：

```
┌────────────────────────────────────────────────────────────────────┐
│                        openspec/                                   │
│                                                                    │
│   ┌─────────────────────      ┌───────────────────────────────┐   │
│   │       specs/        │      │         changes/              │   │
│   │                     │      │                               │   │
│   │  真相的来源         │◄─────│  提议的修改                   │   │
│   │  你的系统           │ 合并 │  每个变更 = 一个文件夹          │   │
│   │  当前如何工作       │      │  包含产物 + 差异               │   │
│   │                     │      │                               │   │
│   └─────────────────────┘      └───────────────────────────────┘   │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

**规格说明**是真相的来源 — 它们描述你的系统当前如何表现。

**变更**是提议的修改 — 它们存在于单独的文件夹中，直到你准备合并它们。

这种分离是关键。你可以在没有任何冲突的情况下并行处理多个变更。你可以在变更影响主规格说明之前审查它。当你归档变更时，其差异会干净地合并到真相来源中。

## 规格说明

规格说明使用结构化需求和场景描述你的系统行为。

### 结构

```
openspec/specs/
├── auth/
│   └── spec.md           # 认证行为
├── payments/
│   └── spec.md           # 支付处理
├── notifications/
│   └── spec.md           # 通知系统
└── ui/
    └── spec.md           # UI 行为和主题
```

按领域组织规格说明 — 对你的系统有意义的逻辑分组。常见模式：

- **按功能区域**：`auth/`、`payments/`、`search/`
- **按组件**：`api/`、`frontend/`、`workers/`
- **按有界上下文**：`ordering/`、`fulfillment/`、`inventory/`

### 规格格式

规格说明包含需求，每个需求都有场景：

```markdown
# 认证规格说明

## 目的
应用程序的认证和会话管理。

## 需求

### 需求：用户认证
系统在成功登录时应签发 JWT 令牌。

#### 场景：有效凭据
- 给定一个拥有有效凭据的用户
- 当用户提交登录表单时
- 然后返回 JWT 令牌
- 并且用户被重定向到仪表板

#### 场景：无效凭据
- 给定无效凭据
- 当用户提交登录表单时
- 然后显示错误消息
- 并且不签发令牌

### 需求：会话过期
系统必须在 30 分钟不活动后使会话过期。

#### 场景：空闲超时
- 给定一个已认证的会话
- 当 30 分钟过去而没有活动时
- 然后会话失效
- 并且用户必须重新认证
```

**关键要素：**

| 要素 | 目的 |
|------|------|
| `## 目的` | 此规格说明领域的高层描述 |
| `### 需求：` | 系统必须具有的特定行为 |
| `#### 场景：` | 需求在行动中的具体示例 |
| SHALL/MUST/SHOULD | RFC 2119 关键字，指示需求强度 |

### 为什么这样构建规格说明

**需求是"什么"** — 它们陈述系统应该做什么，而不指定实现。

**场景是"何时"** — 它们提供可以验证的具体示例。好的场景：
- 是可测试的（你可以为它们编写自动化测试）
- 涵盖快乐路径和边缘情况
- 使用 Given/When/Then 或类似的结构化格式

**RFC 2119 关键字**（SHALL、MUST、SHOULD、MAY）传达意图：
- **MUST/SHALL** — 绝对需求
- **SHOULD** — 推荐的，但存在例外
- **MAY** — 可选的

### 规格说明是什么（以及不是什么）

规格说明是**行为契约**，而不是实现计划。

好的规格说明内容：
- 用户或下游系统依赖的可观察行为
- 输入、输出和错误条件
- 外部约束（安全、隐私、可靠性、兼容性）
- 可以测试或显式验证的场景

规格说明中避免：
- 内部类/函数名称
- 库或框架选择
- 逐步实现细节
- 详细的执行计划（这些属于 `design.md` 或 `tasks.md`）

快速测试：
- 如果实现可以在不改变外部可见行为的情况下更改，它可能不属于规格说明。

### 保持轻量：渐进式严格性

OpenSpec 旨在避免官僚主义。使用仍然使变更可验证的最轻量级。

**轻量级规格说明（默认）：**
- 简短的行为优先需求
- 清晰的范围和非目标
- 少数具体的验收检查

**完整规格说明（用于更高风险）：**
- 跨团队或跨仓库变更
- API/合约变更、迁移、安全/隐私问题
- 模糊性可能导致昂贵返工的变更

大多数变更应保持在轻量级模式。

### 人类 + 代理协作

在许多团队中，人类探索，代理起草产物。预期的循环是：

1. 人类提供意图、上下文和约束。
2. 代理将其转换为行为优先的需求和场景。
3. 代理将实现细节保留在 `design.md` 和 `tasks.md` 中，而不是 `spec.md`。
4. 验证在实施之前确认结构和清晰度。

这使规格说明对人类可读，对代理一致。

## 变更

变更是对你系统的提议修改，打包为包含理解和实现所需一切的文件夹。

### 变更结构

```
openspec/changes/add-dark-mode/
├── proposal.md           # 为什么和什么
├── design.md             # 如何（技术方法）
├── tasks.md              # 实现清单
├── .openspec.yaml        # 变更元数据（可选）：模式、创建日期、skip_specs、retire_capabilities
└── specs/                # 差异规格说明
    └── ui/
        └── spec.md       # ui/spec.md 中正在更改的内容
```

每个变更都是独立的。它有：
- **产物** — 捕获意图、设计和任务的文档
- **差异规格说明** — 对正在添加、修改或删除的内容的规格说明
- **元数据** — 此特定变更的可选配置

### 为什么是文件夹

将变更打包为文件夹有几个好处：

1. **一切在一起。**提案、设计、任务和规格说明都位于一处。无需在不同位置寻找。

2. **并行工作。**多个变更可以同时存在而不会冲突。在处理 `add-dark-mode` 的同时，`fix-auth-bug` 也在进行中。

3. **干净的历史。**归档时，变更移动到带有完整上下文保留的 `changes/archive/`。你可以回顾并理解不仅是什么变了，还有为什么。

4. **易于审查。**变更文件夹易于审查 — 打开它，阅读提案，检查设计，查看规格差异。

## 产物

产物是变更中指导工作文档。

### 产物流

```
proposal ──────► specs ──────► design ──────► tasks ──────► implement
    │               │             │              │
   为什么          什么           如何          步骤
 + 范围          变更          方法          采取
```

产物相互构建。每个产物为下一个提供上下文。

### 产物类型

#### 提案（`proposal.md`）

提案在高层捕获**意图**、**范围**和**方法**。

```markdown
# 提案：添加深色模式

## 意图
用户请求一个深色模式选项以减少夜间使用时的眼睛疲劳并匹配系统偏好。

## 范围
范围内：
- 设置中的主题切换
- 系统偏好检测
- 在 localStorage 中持久化偏好

范围外：
- 自定义颜色主题（未来工作）
- 每页主题覆盖

## 方法
使用 CSS 自定义属性进行主题设置，并使用 React context 进行状态管理。在首次加载时检测系统偏好，允许手动覆盖。
```

**何时更新提案：**
- 范围变更（缩小或扩大）
- 意图澄清（对问题的更好理解）
- 方法根本转变

#### 规格说明（`specs/` 中的差异规格说明）

差异规格说明描述相对于当前规格说明**正在更改什么**。请参阅下面的[差异规格说明](#差异规格说明)。

#### 设计（`design.md`）

设计捕获**技术方法**和**架构决策**。

````markdown
# 设计：添加深色模式

## 技术方法
通过 React Context 管理主题状态以避免 prop drilling。
CSS 自定义属性实现运行时切换，无需类切换。

## 架构决策

### 决策：Context 优于 Redux
使用 React Context 处理主题状态，因为：
- 简单的二进制状态（浅色/深色）
- 没有复杂的状态转换
- 避免添加 Redux 依赖

### 决策：CSS 自定义属性
使用 CSS 变量而不是 CSS-in-JS，因为：
- 与现有样式表一起工作
- 没有运行时开销
- 浏览器原生解决方案

## 数据流
```
ThemeProvider (context)
       │
       ▼
ThemeToggle ◄──► localStorage
       │
       ▼
CSS Variables (applied to :root)
```

## 文件变更
- `src/contexts/ThemeContext.tsx`（新）
- `src/components/ThemeToggle.tsx`（新）
- `src/styles/globals.css`（修改）
````

**何时更新设计：**
- 实现揭示方法行不通
- 发现更好的解决方案
- 依赖项或约束变化

#### 任务（`tasks.md`）

任务是**实现清单** — 带有复选框的具体步骤。

```markdown
# 任务

## 1. 主题基础设施
- [ ] 1.1 创建带有浅色/深色状态的 ThemeContext
- [ ] 1.2 为颜色添加 CSS 自定义属性
- [ ] 1.3 实现 localStorage 持久化
- [ ] 1.4 添加系统偏好检测

## 2. UI 组件
- [ ] 2.1 创建 ThemeToggle 组件
- [ ] 2.2 在设置页面添加切换
- [ ] 2.3 更新 Header 以包含快速切换

## 3. 样式
- [ ] 3.1 定义深色主题调色板
- [ ] 3.2 更新组件以使用 CSS 变量
- [ ] 3.3 测试对比度以满足无障碍要求
```

**任务最佳实践：**
- 将相关任务分组在标题下
- 使用分层编号（1.1、1.2 等）
- 保持任务小到可以在一次会话中完成
- 说明每个任务的验证方式（测试、命令或可观察结果）
- 将每个组的工作所需的测试和文档放在该组内部，而不是放在最后的补漏组中
- 勾选完成的任务

## 差异规格说明

差异规格说明是使 OpenSpec 适用于棕地开发的关键概念。它们描述**正在更改什么**而不是重述整个规格说明。

### 格式

```markdown
# Auth 的差异

## 新增需求

### 需求：双因素认证
系统必须支持基于 TOTP 的双因素认证。

#### 场景：2FA 注册
- 给定一个未启用 2FA 的用户
- 当用户在设置中启用 2FA 时
- 然后显示 QR 码以供认证器应用设置
- 并且用户必须在激活前用代码验证

#### 场景：2FA 登录
- 给定一个启用了 2FA 的用户
- 当用户提交有效凭据时
- 然后呈现 OTP 挑战
- 并且仅在有效 OTP 后完成登录

## 修改需求

### 需求：会话过期
系统必须在 15 分钟不活动后使会话过期。
（之前：30 分钟）

#### 场景：空闲超时
- 给定一个已认证的会话
- 当 15 分钟过去而没有活动时
- 然后会话失效

## 移除需求

### 需求：记住我
（已弃用，改为支持 2FA。用户应在每个会话中重新认证。）
```

### 差异章节

| 章节 | 含义 | 归档时发生什么 |
|---------|---------|------------------------|
| `## 新增需求` | 新行为 | 追加到主规格说明 |
| `## 修改需求` | 更改的行为 | 替换现有需求 |
| `## 移除需求` | 弃用的行为 | 从主规格说明中删除；移除最后的需求会退役能力并删除其规格文件，当变更声明 `retire_capabilities: true` 时 |
| `## 目的` | 全新能力的用途 | 种子正在创建的主规格说明的目的；当规格说明已存在时忽略 |

### 为什么是差异而不是完整规格说明

**清晰度。**差异准确地显示正在更改什么。阅读完整规格说明，你不得不在心理上将其与当前版本进行比较。

**避免冲突。**两个变更可以触及同一规格文件而不会冲突，只要它们修改不同的需求。

**审查效率。**审查者看到变更，而不是未变更的上下文。专注于重要的内容。

**棕地适用性。**大多数工作修改现有行为。差异使修改成为一等公民，而不是事后考虑。

## 模式

模式定义工作流的产物类型及其依赖关系。

### 模式如何工作

```yaml
# openspec/schemas/spec-driven/schema.yaml
name: spec-driven
artifacts:
  - id: proposal
    generates: proposal.md
    requires: []              # 没有依赖项，可以先创建

  - id: specs
    generates: specs/**/*.md
    requires: [proposal]      # 创建前需要提案

  - id: design
    generates: design.md
    requires: [proposal]      # 可以与规格说明并行创建

  - id: tasks
    generates: tasks.md
    requires: [specs, design] # 需要先创建规格说明和设计
```

**产物形成依赖图：**

```
                    proposal
                   (根节点)
                       │
         ┌─────────────┴─────────────┐
         │                           │
         ▼                           ▼
      specs                       design
   (requires:                  (requires:
    proposal)                   proposal)
         │                           │
         └─────────────┬─────────────
                       │
                       ▼
                    tasks
                (requires:
                specs, design)
```

**依赖关系是赋能者，不是关卡。**它们显示可以创建什么，而不是必须创建什么。如果你不需要设计，可以跳过。你可以在 design 之前或之后创建规格说明 — 两者都只依赖于提案。

### 内置模式

**spec-driven**（默认）

规格驱动开发的标准工作流：

```
proposal → specs → design → tasks → implement
```

最适合：大多数功能工作，你想在实现之前就规格说明达成一致。

### 自定义模式

为你的团队工作流创建自定义模式：

```bash
# 从头创建
openspec schema init research-first

# 或分叉现有的
openspec schema fork spec-driven research-first
```

**示例自定义模式：**

```yaml
# openspec/schemas/research-first/schema.yaml
name: research-first
artifacts:
  - id: research
    generates: research.md
    requires: []           # 先做研究

  - id: proposal
    generates: proposal.md
    requires: [research]   # 提案以研究为基础

  - id: tasks
    generates: tasks.md
    requires: [proposal]   # 跳过规格说明/设计，直接进入任务
```

请参阅[自定义](customization.md)了解有关创建和使用自定义模式的完整详细信息。

## 归档

归档通过将变更的差异规格说明合并到主规格说明中来完成变更，并保留变更以供历史查看。

### 归档时会发生什么

```
归档前：

openspec/
├── specs/
│   └── auth/
│       └── spec.md ◄────────────────┐
└── changes/                         │
    └── add-2fa/                     │
        ├── proposal.md              │
        ├── design.md                │ 合并
        ├── tasks.md                 │
        └── specs/                   │
            └── auth/                │
                └── spec.md ─────────┘


归档后：

openspec/
├── specs/
│   └── auth/
│       └── spec.md        # 现在包含 2FA 需求
└── changes/
    └── archive/
        └── 2025-01-24-add-2fa/    # 保留以供历史查看
            ├── proposal.md
            ├── design.md
            ├── tasks.md
            └── specs/
                └── auth/
                    └── spec.md
```

### 归档过程

1. **合并差异。**每个差异规格说明章节（新增/修改/移除）都应用到相应的主规格说明。

2. **移动到归档。**变更文件夹移动到 `changes/archive/` 并带有日期前缀以进行时间顺序排序。

3. **保留上下文。**所有产物在归档中保持完整。你随时可以回顾以理解为什么进行变更。

### 为什么归档很重要

**干净的状态。**活跃变更（`changes/`）仅显示进行中的工作。已完成的工作移出视线。

**审计线索。**归档保留每个变更的完整上下文 — 不仅是什么变了，还有解释原因的提案、解释方法的设计和展示已完成工作的任务。

**规格说明演进。**随着变更归档，规格说明有机增长。每次归档合并其差异，逐步建立全面的规格说明。

## 如何组合在一起

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                              OPENSPEC FLOW                                   │
│                                                                              │
│   ┌────────────────                                                         │
│   │  1. 开始      │  /opsx:propose（核心）或 /opsx:new（扩展）            │
│   │     变更      │                                                         │
│   └───────┬────────┘                                                         │
│           │                                                                  │
│           ▼                                                                  │
│   ┌────────────────┐                                                         │
│   │  2. 创建      │  /opsx:ff 或 /opsx:continue（扩展工作流）             │
│   │     产物      │  创建 proposal → specs → design → tasks               │
│   │                │  （基于模式依赖）                                       │
│   └───────┬────────┘                                                         │
│           │                                                                  │
│           ▼                                                                  │
│   ┌────────────────┐                                                         │
│   │  3. 实现      │  /opsx:apply                                            │
│   │     任务      │  处理任务，勾选它们                                     │
│   │                │◄──── 随着学习更新产物                                  │
│   └───────┬────────┘                                                         │
│           │                                                                  │
│           ▼                                                                  │
│   ┌────────────────┐                                                         │
│   │  4. 验证      │  /opsx:verify（可选）                                   │
│   │     工作      │  检查实现是否匹配规格说明                               │
│   └───────┬────────┘                                                         │
│           │                                                                  │
│           ▼                                                                  │
│   ┌────────────────┐     ┌──────────────────────────────────────────────┐    │
│   │  5. 归档      │────►│  差异规格说明合并到主规格说明                   │    │
│   │     变更      │     │  变更文件夹移动到 archive/                    │    │
│   └────────────────┘     │  规格说明现在是更新的真相来源                   │    │
│                          └──────────────────────────────────────────────┘    │
│                                                                              │
└──────────────────────────────────────────────────────────────────────────────┘
```

**良性循环：**

1. 规格说明描述当前行为
2. 变更提议修改（作为差异）
3. 实现使变更成为现实
4. 归档将差异合并到规格说明
5. 规格说明现在描述新行为
6. 下一个变更基于更新的规格说明构建

## 术语表

| 术语 | 定义 |
|------|------|
| **产物** | 变更内的文档（提案、设计、任务或差异规格说明） |
| **归档** | 完成变更并将其差异合并到主规格说明的过程 |
| **变更** | 对系统的提议修改，打包为包含产物的文件夹 |
| **差异规格说明** | 描述相对于当前规格说明的更改（新增/修改/移除）的规格说明 |
| **领域** | 规格说明的逻辑分组（例如 `auth/`、`payments/`） |
| **需求** | 系统必须具有的特定行为 |
| **场景** | 需求的具体示例，通常采用 Given/When/Then 格式 |
| **模式** | 产物类型及其依赖关系的定义 |
| **规格说明** | 描述系统行为的规格说明，包含需求和场景 |
| **真相的来源** | `openspec/specs/` 目录，包含当前约定行为 |
