## 作用

`domain-modeling` 在你设计时构建和锐化项目的**通用语言**。它挑战与词汇表冲突的术语，在你使用模糊词汇时要求精确的词语，并通过具体场景测试关系，直到边界精确。

它是**主动的**学科，不是被动的。任何技能都可以读取 `GLOSSARY.md` 来借用其词汇。这个技能用于你*正在改变*模型的时候，这就是为什么它会打断你。它在术语确定的那一刻将术语写入 `GLOSSARY.md`，在对话中间，而不是在末尾产生一个整洁的词汇表。末尾写的词汇表是[会话](https://www.aihero.dev/ai-coding-dictionary/session)的摘要；内联版本是会话的输出。

## 何时使用

输入 `/domain-modeling`，或当任务适合时代理自动调用。实际上，自动调用是该技能最弱的部分。当 `grill-with-docs` 或 `wayfinder` 说要加载它时，[模型](https://www.aihero.dev/ai-coding-dictionary/model)经常加载 `grilling` 并跳过这个。如果一个[审问](https://www.aihero.dev/ai-coding-dictionary/grilling)会话结束时 `GLOSSARY.md` 未改变，那就是发生了这种情况。在调用其他技能时，通过名称调用它。

在*词汇*是问题时调用它：

| 情况 | 操作 |
| --- | --- |
| 两个人对"取消"的理解不同 | `domain-modeling`：选择规范术语，将其他术语列在 `_Avoid_` 下 |
| "Account" 在三个文件中做三个工作 | `domain-modeling`：将其拆分为 Customer 和 User |
| 你刚刚做了一个难以逆转的架构选择 | `domain-modeling`：如果该选择通过了门槛，它提供 ADR |
| 模块的*形状*是问题：接缝在哪里、接口有多深 | [codebase-design](https://aihero.dev/skills-codebase-design) |
| 你想在构建之前对整个计划进行审问 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs)，它在底层驱动这个技能 |
| 你想查找术语，而不是改变它 | 什么都不做。读取 `GLOSSARY.md`。它是个文件。 |

## 前置条件

没有前置条件。该技能写入两个地方，并且惰性创建：

- **`GLOSSARY.md`** 在仓库根目录。技能在你确定第一个术语时创建它。在有根目录 `GLOSSARY-MAP.md` 的仓库中，术语会进入地图指向的每个上下文的 `GLOSSARY.md` 中。
- **`docs/adr/`**。技能在第一个通过门槛的 ADR 时创建它。

在开始之前什么都不需要存在，技能不会提前创建任何东西。

## 两个产物，两个门槛

词汇表和 ADR 有不同的门槛。这个技能的大部分麻烦来自于将它们混淆。

| | `GLOSSARY.md` | `docs/adr/NNNN-slug.md` |
| --- | --- | --- |
| 包含 | 术语。一个东西**是什么**，一两句话，拒绝的同义词在 `_Avoid_` 下 | 一个决策，一到三句话：背景、选择、原因 |
| 写入门槛 | 一个模糊术语变成了规范术语 | **全部三个**：难以逆转、没有背景就令人惊讶、真实权衡的结果 |
| 写入时机 | 内联，术语确定的那一刻 | 提供，而非假设 |
| 永远不包含 | 实现细节、[规格说明](https://www.aihero.dev/ai-coding-dictionary/spec)、草稿、通用编程概念 | 本会话做出的每个决策的日记 |

错过 ADR 三个测试中的任何一个，就没有 ADR。一个容易逆转的决策会被直接逆转；一个不令人惊讶的决策没有人的问题；一个没有真正替代方案的决策记录了你做了显而易见的事。

`GLOSSARY.md` 规则最重要，因为它是实践中容易破坏的那个。**它只是一个词汇表，仅此而已。** 如果不加检查，模型会将"写入 `GLOSSARY.md`"视为持久化你给出的每个答案的权限，文件会变成一份运行中的规格说明。这是该技能在整个集合中被报告最多的问题，跨越多个模型。

## 交叉引用，以及它停止的地方

当你陈述某些内容如何工作时，技能会检查代码并指出任何矛盾。"你的代码取消了整个订单，但你刚刚说部分取消是可能的，哪个是对的？" 技能让语言和代码在改变任何一方之前达成一致，大声说出来。

它交叉引用**代码**和已提交的 `GLOSSARY.md` 和 ADR，仅此而已。它不搜索你的问题追踪器。如果你的团队几个月前在已关闭的问题中争论过命名冲突并解决了它，技能会再次提出它，就好像它是新的。有一个[开放请求](https://github.com/mattpocock/skills/issues/717)来修复这个问题。在此之前，变通方案是将其放入你自己的 `docs/agents/domain.md` 中，技能已经读取它。

## 常见问题

**我的 `GLOSSARY.md` 有 500 行。1000 行。3000 行。怎么办？**

大小是症状。原因是文件吸收了不属于词汇表的实现细节和决策。修复方法是一条直接指令：`/grill-with-docs make my GLOSSARY.md more concise and remove any implementation details from it`。针对一个臃肿的文件运行它，大部分内容都会消失。只有在文件精简后仍有两个读者不想同时持有的领域时，才用 `GLOSSARY-MAP.md` 拆分它。拆分一个臃肿的文件会给你几个臃肿的文件。技能的指导目前尚不足以首先防止增长，追踪该问题的 issue 仍然开放。

**为什么是 `GLOSSARY.md` 而不是其他名字？**

这是整个技能集中争论最多的命名问题，且没有确定的答案。反对当前名称的理由是充分的：如果它是"一个词汇表，仅此而已"，`GLOSSARY.md` 就说明了这一点，而且正如一位读者所说，"在 ai 代理中一切都是[上下文](https://www.aihero.dev/ai-coding-dictionary/context)"。支持它的理由是地图：`GLOSSARY-MAP.md` 指向多个 `GLOSSARY.md` 文件的读法很自然，而 `GLOSSARY-MAP.md` 指向 `CONTEXT.md` 就不行，而且 `context` 是 DDD 中有限区域的常用词。至少有一个人纯粹为了重命名该文件而维护本地分支。你也可以这样做，但集合中的每个其他技能都查找 `GLOSSARY.md`，因此重命名意味着修补所有技能。

**`ubiquitous-language` 去哪里了？**

它被移除了，而且没有弃用。它的工作移入了 `domain-modeling`，后者持续维护整个模型，而不是在一次对话中倒出词汇表。词汇执行现在更重要，而不是更少。它在底层运行，在审问、分类和映射之下，而不是作为一个你必须记住的单独通道。

**如何为没有词汇表的代码库获取词汇表？**

明确请求它，而不是等待它积累。`/grill-with-docs help me scaffold my existing repo with a GLOSSARY.md` 是文档化的路径。预期长时间的审问。一位用户报告说文件成型前有 50 多个问题。偶然使用在遗留仓库上构建词汇表太慢了。

**我可以保留领域模型并使用自己的 ADR 格式吗？**

今天不能干净地做到。词汇表一半和 ADR 一半在一个技能中发布，因此一个有既定 ADR 约定的团队（不同模板、不同位置、不同命名）会得到与其内部风格冲突的指令。当前选项是本地复制技能并编辑它，或在仓库自己的代理文档中覆盖 ADR 约定。将两者分开是一个[开放请求](https://github.com/mattpocock/skills/issues/557)。

**词汇表真的能值回票价吗？它是一个需要审查的产物，可能会过时。**

有时不能。DDD 离实现越近用处越小。收益在上游，在命名和概念对齐上，而不是在聚合和层仪式中。同义词控制在命名边界处最重要：模块名、表名、状态枚举、问题标题、CLI 命令。它在普通散文中用处小得多。还有一个反对意见是领域术语压缩了*已经共享它们的人*之间的沟通，而代理对纯英文描述的反应方式相同。按这种理解，词汇表的价值是让你和你的审查者与代理正在做的事情保持一致，而不是让代理变得更好。在一天的构建中，跳过它。而且未经审查、由代理编写的词汇表比没有更糟糕：它充满了自信的主张，后续会话将其视为真实。

**它能把我的模糊提示变成领域语言吗？**

不能，而且也没有计划做这个的技能。你自己都不理解的领域语言一旦写下就没有意义。这个技能在你有理解之后执行精确度；它不会发明你自己没有的词汇。相关的陷阱是在没有建模的情况下使用领域词汇。错误概念上的正确名词会产生读起来正确但实际不正确的输出。

## 正常工作的标志

- 它在句子中间打断你，问你两个东西中你指的是哪一个，而不是选一个然后继续。
- `GLOSSARY.md` 在**对话期间**变化，而不是在末尾一股脑出现。
- 它拒绝为明天可以撤销的东西编写 ADR，并说明三个测试中的哪一个失败了。
- 新条目用一两句话定义一个东西*是什么*，并在 `_Avoid_` 下列出你放弃的词。
- 当你的代码和句子不一致时，它引用你的代码。
- `GLOSSARY.md` 变短的次数和变长的次数一样多。

## 它在何处适用

`domain-modeling` 是一个**模型调用的参考**，它*在底层*运行其他技能的次数比它自己运行的次数多。[grill-with-docs](https://aihero.dev/skills-grill-with-docs) 通过审问会话驱动它，[wayfinder](https://aihero.dev/skills-wayfinder) 在绘制地图时加载它，[triage](https://aihero.dev/skills-triage) 用它来让[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)用项目自己的话书写，[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 在决策确定时调用它。最近的兄弟是 [codebase-design](https://aihero.dev/skills-codebase-design)。两者一起是其他一切的底层词汇层，这个是针对*领域*的，那个是针对模块*形状*的。它也可以直接到达，当你想要学科而不想承诺通常会加载它的技能的步骤时。当你不确定哪种技能适合时，[ask-matt](https://aihero.dev/skills-ask-matt) 会为你路由。
