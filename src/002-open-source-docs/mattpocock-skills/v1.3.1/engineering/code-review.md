## 作用

`code-review` 审查 `HEAD` 与你指定的固定点（一个提交、一个分支、一个标签、`main`、`HEAD~5`）之间的差异，从两个维度进行。**标准**询问代码是否遵循本仓库的编写方式。**规格**询问代码是否满足原始问题或[规格说明](https://www.aihero.dev/ai-coding-dictionary/spec)的要求。每个维度都在自己的[子代理](https://www.aihero.dev/ai-coding-dictionary/subagent)中运行，因此彼此看不到对方的推理过程。

该技能从不合并或重新排序两个维度。报告以每个维度中最严重的问题结束，并且拒绝给出一个跨维度的单一获胜者。一个变更可能通过一个维度而另一个维度失败。遵循所有规范但实现错误内容的代码通过标准但失败规格。完全符合[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)要求但破坏仓库规范的代码则相反。混合的判决会让通过的维度掩盖失败的维度。

## 何时使用

输入 `/code-review`，或当你要求审查分支、PR、工作进度或任何"自 X 以来"的内容时，代理会自动调用它。

| 你的情况 | 使用 |
| --- | --- |
| 存在差异，你想知道它是否构建正确*且*是否是正确的东西 | `code-review` |
| 你想在差异中寻找 bug：空路径、竞态、差一 | Claude Code 自己的内置审查，不是这个（见下面的名称冲突） |
| 尚未编写，希望先写测试 | [tdd](https://aihero.dev/skills-tdd) |
| 整个规格说明需要构建，包括审查 | [implement](https://aihero.dev/skills-implement)，它自己调用这个技能 |
| 整个代码库已经偏移，不是一个差异 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) |
| 某处损坏，不知道原因 | [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) |

你必须提供固定点。如果不提供，技能会要求一个而不是猜测。在产生任何子代理之前，它会检查引用是否可解析以及差异是否为空，因此拼错的分支名会在你面前失败，而不是在两个子代理内部。

## 前置条件

标准维度不需要任何东西。它读取仓库记录的内容（`CODING_STANDARDS.md`、`CONTRIBUTING.md` 等），当仓库没有记录时回退到内置基线。

规格维度需要一个存在且可找到的规格说明。它按以下顺序查找：

1. 提交消息中的问题引用（`#123`、`Closes #45`、GitLab `!67`），通过追踪器文档获取。
2. 你作为参数传递的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支或功能名称匹配的规格文件。
4. 询问你。

第 1 步依赖于追踪器文档，由 [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) 编写。没有它，如果你手动提供路径，该维度仍然可以工作。完全没有规格说明时，技能跳过规格子代理，报告说"无可用规格"而不是发明要求。

## 两个维度

| | 标准 | 规格 |
| --- | --- | --- |
| 问题 | 构建正确吗？ | 这是正确的东西吗？ |
| 读取 | 仓库记录的标准，加上气味基线 | 原始问题或规格说明 |
| 报告 | 记录的违规（可能很严重），以及气味（总是判断） | 缺失或部分要求、范围蔓延、错误实现的要求 |
| 每个发现引用 | 标准文件和规则，或命名的气味加上代码块 | 规格说明的行 |

此设计旨在避免一个不知道你的标准的通用审查技能。这样的技能会标记你代码库中故意为之的内容，并错过你的代码库依赖的不变式。因此仓库自己的文档是标准维度上的[原始来源](https://www.aihero.dev/ai-coding-dictionary/primary-source)，并且**仓库总是优先**。

**气味基线**位于仓库标准之下。它是 Fowler《重构》第 3 章中的 12 种代码气味：神秘名称、重复代码、特性嫉妒、数据泥团、基本类型偏执、重复 Switch、霰弹式修改、发散式变化、投机通用性、消息链、中间人、拒绝继承。每种都是带标签的启发式（"可能的特性嫉妒"），从来不是硬性违规。每种都说明了气味是什么以及如何修复，因此发现附带修复方案而非仅仅是抱怨。两个维度都会跳过你的 linter 已经强制执行的内容。

## 常见问题

**它与 Claude Code 自己的 `/code-review` 冲突。怎么办？**

这是该技能报告最多的问题，且尚未修复。Claude Code 自带 `/code-review`，功能不同：它寻找差异中的 bug，而这个审查规格合规性和仓库标准。当你安装这个库时，其中一个会获胜，取决于你的安装方式：

- **插件市场。** 每个技能都会获得 `mattpocock-skills:` 前缀，内置的变得难以通过非限定名访问。
- **纯技能安装。** 本地文件获胜，这个技能会覆盖内置的。

一个答案是移除 Claude Code 的内置技能。这节省了大量[上下文](https://www.aihero.dev/ai-coding-dictionary/context)，并且冲突不再重要。覆盖本身可以说是 Claude Code [工具链](https://www.aihero.dev/ai-coding-dictionary/harness)的 bug（技能作者应该可以自由命名技能），因此另一个答案是重命名本地副本。`npx skills update` 会撤销对 frontmatter 或重命名目录的编辑。用户报告的持久性变通方案是将技能分叉到一个新名称，并从托管集中移除 `code-review`。记录你分叉的提交，以便手动重新同步。

**它的子代理不断调用 `/code-review` 并产生更多代理。**

这是一个已知的开放 bug。多人在多个工具链中复现了它。标准和规格提示禁止委托，因此子代理可以再次找到该技能并再次扩散。一份报告达到了超过 50 个代理。人们在分支上应用的修复是在两个子代理简报中各追加一行："不要调用 `/code-review` 或产生额外代理：直接执行此审查。"有些人更喜欢在工具链层面处理，以便每个技能继承保护。两者都尚未随技能一起发布。如果你无人值守运行此技能，请监视代理数量。

**我应该在编写代码的同一[会话](https://www.aihero.dev/ai-coding-dictionary/session)中运行它吗？**

更喜欢新的会话。正如一位读者所说："同一上下文审查自己不是审查，是带有斜杠命令的确认偏差。"在编写会话中审查的代理拥有塑造代码的每一个假设。独立审查者不会有该上下文。这也是为什么人们要求[implement](https://aihero.dev/skills-implement)不带内置审查步骤，因为该步骤在刚才编写差异的会话内运行审查。独立版本是从干净会话自行调用 `/code-review`。

**每个工单之后还是最后一次性审查？**

两者都有效，技能不替你决定。每个工单保持差异足够小，使规格维度有一个明确的规格可检查，这是 `implement` 使用的方式。在分支末尾批量处理可以捕捉每个工单单独通过时遗漏的工单间交互。如果你不确定，每个工单审查，然后对分支点进行一次最终审查。

**我能信任发现吗？**

不能未经检查就信任。子代理输出是假设，不是证据。一个团队报告了基于散文的审查遗漏的十几个破坏性变更。技能将两份报告原样合并，或进行轻微清理。它不会针对每个声明重新验证文件，因此发现可能引用错误位置或夸大影响。在采取行动之前阅读每个发现的引用。技能要求每个发现都附带引用（标准规则、气味加代码块或规格行），这使发现可检查。

**为什么我每次运行它都会发现新问题？**

每次修复都会增加新的代码需要审查，标准维度中判断性的那一半每次运行都会给出不同结果。一位读者描述了循环："/code-review 和 /improve-code-architecture 每次都发现新东西。我实施修复，重新运行这些技能，一次又一次。"没有收敛保证。将一次通过视为线索列表。根据有引用规则支持的线索采取行动，然后停止。不要循环运行直到它返回干净，因为它永远不会。

**它会审查我未提交的工作吗？**

不会。它对比 `<fixed-point>...HEAD`。三点形式从合并基线测量，排除暂存和工作树变更。如果 `implement` 没有进行临时提交，审查就看不到即将进入下一次提交的工作。先提交，然后审查，然后修正或添加修复。

## 正常工作的标志

- 它在坏的引用或空差异之前拒绝开始，在任何子代理产生之前。
- 报告以 `## 标准` 和 `## 规格` 下的两个独立块到达，而不是一个合并列表。
- 每个标准发现都命名你仓库文件中的规则或 12 种气味之一，并引用代码块；每个规格发现都引用规格说明的一行。
- 结束摘要给出每个维度中最严重的问题，并拒绝选出总体赢家。
- 没有可用规格时，规格块明确说明，而不是列出从代码中推断的要求。

## 它在何处适用

`code-review` 是构建链尾部附近的审查步骤：`grill-with-docs → to-spec → to-tickets → implement → code-review → retro`。它也独立存在于你指向的任何分支或 PR 上。

- [implement](https://aihero.dev/skills-implement) 是最近的邻居。它驱动构建并作为自己的结项审查调用此技能。[implement-spec](https://aihero.dev/skills-implement-spec) 在整个集成分支上做同样的事。
- [retro](https://aihero.dev/skills-retro) 在它之后并进行调整。当会话显示审查遗漏了一类错误时，`retro` 建议检查或标准轴随后读取的 `CODING_STANDARDS.md` 规则。
- [pr](https://aihero.dev/skills-pr) 在审查工作提交后编写 PR 正文。
- [to-spec](https://aihero.dev/skills-to-spec) 和 [to-tickets](https://aihero.dev/skills-to-tickets) 产生规格维度检查的文档，因此模糊的规格使该维度模糊。
- [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 是整个代码库的对应物，因为此技能只查看一个差异。

[ask-matt](https://aihero.dev/skills-ask-matt) 在你不确定哪种技能适合当前情况时在整个集合中进行路由。
