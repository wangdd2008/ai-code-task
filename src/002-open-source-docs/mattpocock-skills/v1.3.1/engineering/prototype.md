## 作用

`prototype` 编写**回答一个问题的可丢弃代码**：这个状态模型感觉对吗，或者这个屏幕应该长什么样。问题在前，决定你构建什么。回答错误问题的原型是浪费的，无论它看起来多好。

可丢弃是代码如何*编写*的约束，不是销毁它的承诺。没有测试，没有超出使其运行的错误处理，没有抽象，没有持久化，因为这些都没有帮助你学习你试图学习的唯一一件事。有两样东西存活下来。答案进入真实代码，原型则放到一个分支上，作为答案的证据。

## 何时使用

输入 `/prototype`，或者当任务适合时 [agent](https://www.aihero.dev/ai-coding-dictionary/agent) 会自动使用它。

在你遇到无法通过交谈解决的问题时立即使用它：一个你无法在脑海中掌握边缘情况的状态机，一个直到看到三个并排版本才能想象的屏幕。[grilling](https://www.aihero.dev/skills-grilling) 会话在这些问题上会变得冗长。agent 会重新表述，你猜，范围扩大。停止 grilling，构建可丢弃版本，看看它，然后一句话回答。如果某个已经构建的东西行为异常，你想知道为什么，使用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)；原型探索要构建什么，而不是为什么构建的东西坏了。

你也会不自觉地来到这里。[wayfinder](https://aihero.dev/skills-wayfinder) 会在它的地图上提交 `prototype` 决策 [tickets](https://www.aihero.dev/ai-coding-dictionary/ticket)，你用这个技能处理它们。

## 两个分支

问题决定分支，分支产生不同的产物：

- **"这个逻辑 / 状态模型感觉对吗？"**：一个**可共享的 HTML 文件**。一个自包含的页面，没有构建也没有服务器，双击打开即可。它带有一个标记状态面板，每次点击后重新渲染，自由播放按钮可以任意顺序戳模型，以及标签式**引导式演练**（每个标签一个场景，下面有按顺序排列的按钮）。所有内容都用领域语言标记，所以你可以把它交给设计师、PM 或领域专家，让他们自己尝试模型。页面背后的逻辑是一个小型纯模块（reducer、machine、一组函数），没有 DOM 代码，所以你可以将验证过的版本直接移到真实代码中。
- **"这个应该长什么样？"**：几个**截然不同的** UI 变体，在同一路由上，可通过浮动底部栏和 `?variant=` URL 参数切换。变体必须在结构上不认同，而不是颜色；三个卡片网格的小调整回答不了任何问题。它们在真实页面中渲染，尽可能使用真实数据和真实密度，因为在空白页面上判断的变体总是看起来不错。

两者都保持状态在内存中，无需设置，每步之后都展示完整状态。当你开始硬化其中一个时（添加测试、连接真实数据库、泛化一个可能以后用的用例），你就已经停止原型了。

## 原型是一级来源

完成的原型留下两样东西，它们去不同的地方。

你记录**答案**（裁决加上它解决的问题）到某个永久的地方：提交消息、ADR、实现 issue。主分支保留答案，在真实代码中。

**原型**是答案来源的可运行证据，你不删除它。它也不属于主分支，因为没有人维护它，而且很快会过时。所以你把它提交到一个从主分支分出的 `prototype/<name>` 分支，永远不要合并，并在实现 issue 上留下一个 [context pointer](https://www.aihero.dev/ai-coding-dictionary/context-pointer) 指向那个分支。主分支保持干净，接手工作的人可以找到并重新运行原型。

## 常见问题

**等等，原型不是要删除的吗？**
不再是了。以前是的：构建它，保留答案，丢弃代码。最有力的反对意见不是关于速度。而是*下一个 [session](https://www.aihero.dev/ai-coding-dictionary/session) 接手工作的人是谁，他们有什么可以工作的？*原型的散文总结会失去使其令人信服的东西。所以技能现在将原型视为一级来源。它落在主分支外的 `prototype/<name>` 分支上，实现 issue 指向它。变化的是代码在哪里，而不是纪律；它仍然永远不会合并到主分支。

**它以前构建终端应用。那个去哪了？**
逻辑分支现在发出一个可共享的 HTML 文件。终端应用只能由克隆了仓库并安装了运行时的人驱动，这排除了原型需要其意见的人：设计师、PM、知道状态模型应该是什么的领域专家。一个双击打开、发邮件后仍然有效的自包含文件可以被任何人驱动。下面的纯逻辑模块没有变化，仍然是你要移到真实代码中的部分。

**一个 agent 告诉我应该 `/prototype`，而我已经在实现了。**
这是一个已知的命名问题。不知道流程的 agent 看到 `prototype` 这个词——一个通用且有吸引力的词——一旦 tickets 存在，就认为是"显而易见的下一步"。所以 agent 即使设计已在对话中确定，也会按名字推荐它。如果你已经知道要构建什么，下一步是 `/implement`，每个 ticket 一个。只在具体的设计问题未解决且交谈无法解决时才使用原型。

**我应该在构建任何生产功能之前原型整个应用吗（比如向潜在客户演示）？**
那是一个碰巧共享这个技能名称的不同产物。这里的原型范围是一个问题，"整个应用是什么？"不是一个。全应用原型没有自然的停止点，所以它会漂移成为生产应用：清理永远不会发生，按原型规则（没有测试，没有错误处理）编写的代码最终会出现在用户面前。如果你需要销售演示，故意构建一个 demo 并明确说明其中没有生产代码。如果你需要解决设计问题，把它缩小到那个问题。

**如何在它自己的 session 中运行它？**
原型生活在自己的目录中，并产生大量你不想在提问的线程中的 [context](https://www.aihero.dev/ai-coding-dictionary/context)，所以在其他地方运行它，只带回答案。使用 [handoff](https://aihero.dev/skills-handoff) 将工作移到那个 session，并把答案带回来。

**这不是烧钱最快的方式吗？**
如果你原型化可以通过交谈回答的问题，或者让一个原型蔓延到整个功能，它可能是。重要的比较不是 tokens 对零；而是 [tokens](https://www.aihero.dev/ai-coding-dictionary/token) 对构建错误的状态模型并在它有生产调用者之后才发现。保持问题狭窄，运行简短，花费就会成比例。

## 正常工作的标志

- 你能用一句话说出原型存在是为了回答什么问题，而且它写在演示顶部，不仅仅在你的脑海中。
- 不读代码的人可以驱动逻辑演示。他们打开文件，在演练标签中按按钮，并用自己的话描述他们看到的东西。
- 有人说"等等，那不应该发生"或"嗯，我以为是 X"。那是*想法*中的 bug，而原型就是为了这个。
- UI 变体在布局和信息层级上不认同，而不仅仅是颜色和文案，你得到的反馈是"B 的 header 加上 C 的 sidebar"。
- 它在一个 sitting 中回答。如果你一天后还在构建它，问题太大了；拆分它。
- 结束时，主分支包含决策，不包含任何原型，实现 issue 指向仍然持有它的分支。

## 它在何处适用

`prototype` 是一个**随时可用的独立工具**：你用它来解决一个设计问题，然后回到你的工作。另一个经常运行它的技能是 [wayfinder](https://aihero.dev/skills-wayfinder)。wayfinder 地图由**决策 tickets** 组成，而 `prototype` 是四种类型之一的 ticket：用于当阻塞问题是"这个应该长什么样"或"它应该如何表现"时，多少讨论都无法解决。当讨论模糊时，wayfinder 制造具体的东西来反应，而这个技能构建那个东西。答案解决原型 ticket，地图将原型链接为资产。

其他邻居在那个的上游和下游。[grill-me](https://aihero.dev/skills-grill-me) 和 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 回答可 grilled 的问题；不可 grilled 的来这里，一句话答案回到访谈。下游，验证过的状态模型或 UI 方向成为 [to-spec](https://aihero.dev/skills-to-spec) 的确定输入，它可以内联原型产生的内容丰富的片段，而不是用散文描述它。对于其他一切，[ask-matt](https://aihero.dev/skills-ask-matt) 会为你路由。
