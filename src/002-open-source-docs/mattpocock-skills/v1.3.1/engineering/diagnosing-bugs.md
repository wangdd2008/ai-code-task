## 作用

`diagnosing-bugs` 对难以解决的 bug 或性能回归运行六阶段诊断：构建复现、最小化、排序假设、插桩、修复并回归测试、清理。

它不会让代理形成理论，直到**紧凑**的反馈循环存在：一个已命名的命令，已经运行过一次，在这个 bug 存在时变红，修复后变绿。给定一个 bug 报告，编码代理默认读取代码并猜测。这个技能阻止了这一点。如果没有红变能力的命令存在，就没有第二阶段。这一道门就是该技能的意义所在。一旦循环存在，之后的所有内容（二分、假设测试、插桩）都是机械的。

## 何时使用

输入 `/diagnosing-bugs`，或当任务适合时代理自动调用。它是模型调用的，在"诊断"或"调试这个"，或报告某些内容损坏、抛出、失败或变慢时触发。

在难以解决的 bug 上使用它：一眼看不出的 bug、间歇性闪烁、在两个已知良好状态之间引入的回归。它故意慢而彻底，因此对于一个你想在一条消息中得到答案的问题来说是错误的工具。

| 你的情况 | 去哪里 |
| --- | --- |
| 一个可以描述为症状的具体缺陷 | 这个技能 |
| 一个慢端点或已知的 before-and-after 时间回归 | 这个技能。它有一个性能分支（测量基线，然后二分） |
| "这个代码库的瓶颈在哪里？"，没有具体症状 | 不是这个技能。它诊断一个已知的失败，而不是审计 |
| 来自其他人的原始 bug 报告，尚未确认或记录 | [triage](https://aihero.dev/skills-triage) 优先 |
| 回答设计问题的可丢弃代码，不是追踪缺陷 | [prototype](https://aihero.dev/skills-prototype) |
| 按测试优先构建计划的行为 | [tdd](https://aihero.dev/skills-tdd) |
| 问什么可以防止 bug，一旦修复 | [retro](https://aihero.dev/skills-retro)，在同一会话中运行 |
| 没有好的接缝来锁定 bug | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)，你自己启动 |

## 紧凑循环就是这个技能

第一阶段获得最大努力，因为它是唯一困难的阶段。技能列出了构建循环的方法，大致按偏好排序：

1. 在到达 bug 的任何接缝处的失败测试。
2. 针对运行中的 dev server 的 curl 或 HTTP 脚本。
3. 带有夹具输入的 CLI 调用，与已知良好的快照进行 diff。
4. 对 DOM、控制台或网络进行断言的无头浏览器脚本。
5. 重放捕获：保存的请求、负载或事件日志，在隔离状态下通过代码路径运行。
6. 一个可丢弃的工具链：系统的最小子集，一个函数调用。
7. 属性或模糊循环，用于"有时输出错误"。
8. 你可以交给 `git bisect run` 的二分工具链。
9. 差分循环：相同输入，旧版本与新版本对比。
10. 最后手段的[人工参与循环](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop) bash 脚本。技能为此提供 `scripts/hitl-loop.template.sh`：代理运行脚本，你在终端中遵循提示，你的答案作为可解析的输出返回。

*一个*循环不是目标。**紧凑**才是：快速（秒级）、确定性（每次运行相同判决）、尖锐（断言你的确切症状，而非"没有崩溃"）、代理无需你介入即可运行。一个 30 秒的闪烁循环几乎不比没有好。对于只偶尔出现的 bug，目标不是一个干净的复现，而是一个**更高的复现率**：循环触发器、并行化、增加压力、注入睡眠，直到闪烁率足够高以进行调试。

当代理无法构建一个时，技能告诉它停止并说明情况，列出它尝试了什么，并向你请求[环境](https://www.aihero.dev/ai-coding-dictionary/environment)访问、捕获的产物或添加临时插桩的权限。它不能继续形成假设。

## 阶段之间的门

阶段是门，不是清单。代理不能进入一个阶段，直到特定条件为真。

| 门 | 必须为真 |
| --- | --- |
| 进入第二阶段 | 一个已命名的命令，已经运行并粘贴了其输出，可以在这个 bug 上变红 |
| 进入第三阶段 | 复现已被复现*且*最小化：每个剩余元素都是复现 bug 所必需的 |
| 进入第四阶段 | 存在 3-5 个排序的、可证伪的假设，每个都陈述其预测，在测试任何一个之前展示给你 |
| 进入第五阶段 | 探针映射到特定预测，一次一个变量，每个调试日志都有 `[DEBUG-a4f2]` 之类的标签，因此一次 grep 就能找到它们全部进行清理 |
| 完成 | 原始复现不再复现，插桩已移除，提交消息命名了最终正确的假设 |

第五阶段有一个例外。代理在修复之前编写回归测试，但仅当存在**正确的接缝**时：测试在调用点以真实 bug 模式行使 bug 的地方。当唯一可用的接缝太浅时，技能告诉代理说明情况，而不是编写一个给人虚假信心的测试。缺失的接缝本身就是一个发现，代理记录它而不是隐藏它。

## 常见问题

**它在快速问题上触发，而我只是想要一个直接答案。**

这是该技能报告最多的问题。在 GPT-5.6-Sol 上尤其如此，用户报告它在简单描述问题时触发了相当正式的 diagnosing-bugs 技能："模型触发了相当正式的 diagnosing-bugs 技能。它继续构建复现场景（通常构建一个价值有限的模拟场景），然后才给我回复或建议。这导致相当大的回复延迟。"四个人在 [issue #578](https://github.com/mattpocock/skills/issues/578) 上报告了同样的问题。接受的修复是从更轻的方法开始，只在问题需要时才移动到完整诊断，但该更改尚未发布。该技能针对 Claude Code 的调用行为进行了调优，而[模型](https://www.aihero.dev/ai-coding-dictionary/model)激活阈值较低会过于频繁地触发它。在修复发布之前，变通方案是说出你想要什么（"直接回答，不要诊断"）或在你的[工具链](https://www.aihero.dev/ai-coding-dictionary/harness)中禁用它的模型调用。

**我可以指向一个代码库并问性能问题在哪里吗？**

不能。它诊断一个你已经可以命名的失败。它的性能分支是针对有症状的回归（建立基线测量，然后二分，先测量后修复），而不是主动扫描。一个主动版本的技能曾被[提议并关闭](https://github.com/mattpocock/skills/issues/431)；目前没有技能做这个。

**它在写修复之前停下来问我吗？**

不。只有第三阶段有人工检查点：排序的假设列表在测试任何一个之前展示给你，如果你不在，代理继续自己的排序。插桩和修复之间没有门，因此代理可以在你同意其根本原因之前就开始编写代码。[Issue #124](https://github.com/mattpocock/skills/issues/124) 要求设置该门，仍然开放。如果你想要它，在调用技能时说明。

**我已经对此 bug 报告运行了 `/triage`。这是同样的工作吗？**

部分，而且两个技能都没有说。正如一位读者所说："分类的第三步本质上是 diagnosing-bugs 第一到二阶段的浅层、有界实例，但两个文件都没有提到对方。"分类做一个有界的"这实际上是不是一个 bug，以及表面是什么"的通过；这个技能做彻底的版本。先运行分类不是浪费，因为它的验证通常给你第一阶段的大部分原始材料。但预期这个技能会完整重做这项工作，而且预期没有交叉引用告诉你这一点。

**它粘贴的复现输出会泄露秘密吗？**

可能会。技能要求代理粘贴调用及其输出，并请求 HAR 文件、日志转储和核心转储等产物。没有指令告诉代理对它们进行清理。[Issue #674](https://github.com/mattpocock/skills/issues/674) 正好提出了这一点（凭证、令牌、cookie 和个人数据被复制到聊天、问题或 PR 中），并提出了一个编辑护栏。它处于开放且未实现状态。目前将编辑视为你的工作，特别是在输出进入任何公共领域之前。

**我的安全扫描器将此技能标记为高风险。**

Snyk 标记了它，该标记是误报。它是集合中唯一附带可执行 shell 脚本（`hitl-loop.template.sh`）的技能，并附带运行它的指令以及 curl 开发服务器。一个发布的 `.sh` 文件、运行它的指令和出站 HTTP 在一起足以触发静态扫描器。脚本本身大约 30 行 `read -r -p` 提示，等待人工输入。扫描器评估的是技能*可能*做什么，而不是已证明的漏洞。

**`/diagnose` 怎么了？**

v1.0.0 将其重命名为 `/diagnosing-bugs`。旧名称不再存在。任何你的链式调用 `/diagnose` 的内容（包装技能、保存的提示）都需要更新。

## 正常工作的标志

- 它在提供任何理论之前向你展示一个命令及其红色输出。如果理论先到达，技能没有运行。
- 它复现的失败是你报告的，而不是它在途中发现的附近的一个。
- 它在开始猜测之前缩小复现，并能告诉你为什么需要每个剩余部分。
- 它在测试任何一个之前向你展示 3-5 个假设的排序列表，每个都有你可以证伪的预测。
- 它添加的每个调试日志都带有 `[DEBUG-a4f2]` 之类的标签，对该标签的 grep 在它声明完成时返回空。
- 提交或 PR 消息命名了哪个假设是正确的。
- 当它无法用测试锁定 bug 时，它说明情况而不是编写一个浅测试。

## 它在何处适用

`diagnosing-bugs` 是一个随时可取用的独立技能。你在某些内容损坏时启动它，在修复及其回归测试完成时结束。它保持状态且不需要先前设置。[ask-matt](https://aihero.dev/skills-ask-matt) 路由"某些内容损坏"到这里。

两个邻居重要。[retro](https://aihero.dev/skills-retro) 在它之后：一旦修复完成，在同一会话中运行它，问什么可以防止 bug，而会话拥有的信息比开始时更多。`diagnosing-bugs` 从不自行调用 `retro`，因为 `retro` 是用户调用的。[triage](https://aihero.dev/skills-triage) 在它之前，针对作为来自其他人的原始报告到达的 bug，并做同样前两个阶段的更浅版本。
