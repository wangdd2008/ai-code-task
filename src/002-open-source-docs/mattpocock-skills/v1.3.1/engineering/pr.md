## 作用

`pr` 定义了 pull request 正文的形状：**摘要**展示变更，**证据**证明它有效，以及**合并危险**评估落地风险。它是一个格式参考，不是一个工作流。它不会推送分支、打开 PR 或决定其中包含什么。它告诉 [agent](https://www.aihero.dev/ai-coding-dictionary/agent) 在写 PR 正文时应该是什么样子。

摘要是视觉的，而不是段落。默认的 PR 正文用散文描述 diff。这个技能选择**最小的视图**来清晰表达关键点（伪代码、调用树、组件树、文件树、Mermaid 图或 shape diff），并保持周围的文字简短。审查者已经打开了 diff，所以正文在读取之前就展示了它的形状。

## 何时使用

输入 `/pr`，或者 agent 在写 PR 正文时会自动使用它。

| 你的情况 | 使用 |
| --- | --- |
| 一个分支已准备好，需要审查者可以扫描的正文 | `pr` |
| 代码已写好，但还没有人审查 | 先用 [code-review](https://aihero.dev/skills-code-review)，再用 `pr` |
| PR 已打开，审查评论正在返回 | 这个集合中还没有；`pr` 只写正文 |

## 模板

三个部分，按此顺序：

- **摘要**：一个或多个小视觉元素，每个放在它支持的短文本旁边。使用一个，有时几个，很少全部。只保留审查者需要的调用、文件、props 和边界。
- **证据**：前后对比。当变更是视觉的且 [环境](https://www.aihero.dev/ai-coding-dictionary/environment) 可以截图时，截图是最有力的证据。否则，使用确切失败的测试现在通过的伪代码，或者发生变化的控制台输出。
- **合并危险**：变更是否是**单向门**或**双向门**，以及其**爆炸半径**。双向门很容易撤销；单向门（破坏性迁移、公共 API 移除、难以撤销的决策）则不行。爆炸半径指如果变更出错可能破坏什么：布局偏移、API 消费者、移动端响应性。

门的判断是核心思想。它将"合并是否安全？"从直觉转变为审查者可以反驳的明确声明。它还告诉他们在哪里花费 [人工审查](https://www.aihero.dev/ai-coding-dictionary/human-review) 的时间。快速浏览一个爆炸半径小的双向门，慢慢阅读一个单向门。

## 常见问题

**我能信任 agent 自己的门的判断吗？**

不能盲目信任，而这是声明它的意义。写变更的 agent 也是给它打分的 agent，所以当它说"双向，爆炸半径小"时，要最为怀疑。diff 还经常隐藏变更是否可以撤销。正如一位用户所说，"回滚一个提交不会取消发送一批电子邮件"，而标记的 rollout 只有在第一次写入新格式之前才是双向的。技能给了 agent 一个定义（破坏性操作和难以撤销的决策是单向的），而不是一个清单，所以最仔细地检查合并危险行。有两件事有帮助：确保 agent 面前有 [ticket](https://www.aihero.dev/ai-coding-dictionary/ticket) 或 [spec](https://www.aihero.dev/ai-coding-dictionary/spec)，而不仅仅是 diff；并记下你的仓库始终视为单向的变更（模式迁移、任何对外发布或删除的东西），放在 agent 在做判断之前会读到的地方。

**它会帮我打开 PR 吗？**

不会。`pr` 只覆盖正文。[implement](https://aihero.dev/skills-implement) 在当前分支上结束。请求一个打开 PR 的技能或选项（一个 `/to-pr`，或 `implement` 打开 PR 而不是提交）仍然是开放提案。一位用户的变通方法是一个一句本地覆盖 `implement` 的 skill，告诉它打开 PR。[implement-spec](https://aihero.dev/skills-implement-spec) 是例外：当你的 issue tracker 通过 PR 关闭工作，或者你要求一个时，它会打开 draft PR。因为 `pr` 是 model-invoked 的，agent 在你要求它打开 PR 时会使用这种形状来写正文。

**它不会只是产生另一堵文字和图表墙吗？**

技能旨在防止这种情况，但它仍然可能发生。用户对 agent PR 正文的抱怨是一致的："很长的摘要，但我需要知道的是变更了什么、如何验证、什么可能破坏、以及是否安全合并。"技能告诉 agent 跳过前言，保持散文简短，选择最小的视图——通常一个视觉元素，很少全部。如果你仍然得到一堆图表，agent 忽略了这一点。如果正文很大是因为 diff 很大，问题是 PR 的大小，而 `pr` 不会为你拆分它。

**我的仓库已经有 PR 模板了。哪个优先？**

默认情况下，两者都不优先。`pr` 有自己的模板，不会查找 `.github/pull_request_template.md` 或类似的东西。几位用户要求技能使用仓库的模板。如果你什么都不做，agent 对同一个文档有两个冲突的指令。在你的仓库的 agent docs 中解决它，例如填写仓库模板并在其下放置摘要、证据和合并危险。

**输出是 HTML 吗？为什么 Mermaid 图不渲染？**

输出是 markdown PR 正文，不是 HTML 页面。GitHub 和 GitLab 在 PR 描述中渲染 Mermaid 块，但终端不渲染，所以 agent 在本地展示时图看起来像是原始文本。CLI harness 上的用户通过 ASCII Mermaid 渲染器或让 agent 附加 HTML 版本来解决。Mermaid 是六种视图之一。调用树、文件树或 shape diff 在任何地方读起来都一样。

**它能整理返回的审查评论吗？**

不能。它写正文就停止了。用户不止一次要求一种方法来分流其他开发人员或审查机器人的评论（哪些值得处理，哪些不是问题）。这个技能做不到。

**它会在 PR 变更时保持正文最新吗？**

不会。它在某一时刻写正文，一个在审查下变更的 PR 会使那个正文过时。在大的变更之后请 agent 重写正文。agent 再次写 PR 正文，所以使用相同的形状。

**我的变更没有 UI。证据里放什么？**

除了截图以外的所有东西。截图只在变更是视觉的时候是最有力的证据。对于迁移、后台作业或重构，证据是在此之前失败现在通过的精确测试，或者发生变化的控制台输出。"测试是绿色的"本身是一个声明，而不是前后对比。

**它能将正文标记为由 LLM 撰写吗？**

不能自动标记。一位用户的方法是在仓库的 agent docs 中放一个固定指令，agent 写的每个 issue、评论和 PR 都以披露行结束。这个规则属于仓库，涵盖 agent 发布的所有内容，而不是一种文档的模板。

## 正常工作的标志

- 仅从摘要视觉就能知道 PR 变更了什么，无需打开 diff。
- 正文没有前言：它从摘要标题开始。
- 证据部分展示前后对比，而不是声称测试通过。
- 每个 PR 都声明了门和爆炸半径，单向门是你放慢速度的那些。

## 它在何处适用

`pr` 在审查和 retro 之间，当构建以 pull request 形式发布时：`to-spec → to-tickets → implement → code-review → pr → retro`。它也是 model-invoked 的，所以 agent 在链外写 PR 正文时也会自动使用它。

- [code-review](https://aihero.dev/skills-code-review) 在它之前运行，因为 PR 正文应该描述一个已经被审查的 diff。
- [implement](https://aihero.dev/skills-implement) 产生正文描述的提交。

[ask-matt](https://aihero.dev/skills-ask-matt) 是整个集合的路由器，当你不确定哪种技能适合当前情况时。
